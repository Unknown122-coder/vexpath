# 05 · Roadmap and Milestones

Each milestone ends with something usable and demonstrable. Acceptance criteria are binary. Nothing from a later milestone starts until the current one's criteria pass in CI.

## M1 · SBOM + matching CLI (first usable tool) — **complete 2026-11-09**

Delivered:
- `core.sbom`: CycloneDX 1.4 to 1.6 JSON read and 1.6 write, validated against the official schemas; SPDX 2.2 and 2.3 JSON and tag-value read and write, checked structurally; format detected from content, not filename.
- Seven native lockfile parsers: `uv.lock`, `poetry.lock`, `pdm.lock`, `Pipfile.lock`, pinned `requirements*.txt`, `package-lock.json` v2 and v3, `pnpm-lock.yaml` v6 and v9. Each yields exact versions, directness, scope, and the dependency graph where the format records one. Unpinned requirements are refused with the remedy rather than resolved.
- `core.versions`: PEP 440 and semver ordering per ecosystem, and the OSV range algorithm including reopened ranges. Ecosystems with no precise comparator raise rather than guess.
- `core.cvss`: CVSS 3.0 and 3.1 base scores computed from the vector, verified against nine published vectors. CVSS 4.0 is carried unscored, because its score is a lookup table rather than a formula.
- `core.advisory`: OSV normalisation (identifier selection preferring CVE, severity from the vector, repository discovery, symbols from `ecosystem_specific`), a snapshot source and a live OSV API source, and bulk sync from the OSV ecosystem exports with alias-aware deduplication.
- `core.vulnmatch`: matching with withdrawn advisories excluded, unorderable versions reported as under investigation, nearest-fix advice, and worst-first ordering.
- `core.scan` and `core.report`: the pipeline, plus terminal, Markdown and SARIF 2.1.0 rendering from one source.
- CLI: `vexpath scan` (table, JSON, Markdown, SARIF), `vexpath sbom generate|validate|lockfiles`, `vexpath advisory sync|show|coverage`, with stdout reserved for machine output.
- Worker: `sync-advisories` downloads, snapshots, optionally loads, and measures symbol coverage against a stated floor.
- A scheduled workflow that refreshes the corpus, publishes it as an artefact and puts symbol coverage in the job summary.

Acceptance met:
- Every fixture SBOM parses; the CycloneDX this project emits satisfies the official 1.6 schema; the CycloneDX and SPDX fixtures for the same project agree on their component set.
- Generation is deterministic: an unchanged project produces the same digest and the same serial number across runs.
- 348 unit tests pass, lint and formatting are clean, `mypy --strict` reports no issues across 53 source files.

Deviations from the original plan, and why:
- **Parity with `osv-scanner` is not asserted.** Comparing against another tool's output requires both to read the same live corpus, which makes the check unreproducible and dependent on a third party's release schedule. The equivalent guarantee is tested directly instead: name normalisation, range evaluation including reopened ranges, and withdrawn-advisory exclusion each have their own tests.
- **The first real symbol-coverage number is not in yet.** `vexpath advisory coverage` and the scheduled workflow measure it, but running a full OSV download has not happened here. That measurement is the first task of M2, and it gates the call-graph work.
- **EPSS and CISA KEV enrichment is deferred to M2.** The fields, the storage and the reporting exist; only the two daily feeds are not wired up. They change prioritisation, not whether a finding is reported.

## M2 · Reachability for Python (the differentiator) — **in progress**

### Done: the engine

The analysis itself works end to end, offline, against the fixture suite.

- `core.reach.graph`: call-graph structures, two-level linking as a dictionary
  union, and a search that answers "certainly reachable" and "possibly
  reachable" as two separate breadth-first passes. Collapsing those two would
  either overstate certainty or bury real findings, so they never share a code
  path.
- `core.reach.pybuild`: the Python builder. Resolves direct calls, imports,
  methods on an inferred class (from an assignment, a parameter annotation, or
  `self.attr = Foo()`), methods on `self`, inherited methods, subclass
  overrides, and re-exports through a package's `__init__`. Marks functions
  opaque when they use `eval`, `exec`, a dynamic import, or `getattr` on a
  computed name. Counts every unresolved call site so the quality travels with
  the verdict.
- `core.reach.entrypoints`: configuration, console scripts, main guards, and
  framework conventions (web routes, Celery tasks, Click and Typer commands,
  Django management commands and URL configurations, serverless handlers,
  application objects), with the public-function fallback reported as inferred.
- `core.reach.verdict`: the verdict rules, including every refusal.

Two design decisions emerged from building it, both now enforced in code:

- **Importing a module does not reach the functions it defines.** Treating
  definition as execution would make every function of every installed package
  reachable, and nothing could ever be cleared. Imports reach module-level
  code, class bodies and decorators, which do run; function bodies are reached
  only by a call.
- **A dependency whose own graph is unavailable can never be cleared.** A
  direct call to a vulnerable symbol is still visible, so "reachable" stays
  sound, but an absence of paths through code the analysis could not see proves
  nothing. That case reports `package_not_analysed`, not `unreachable`.

All six fixtures produce their declared verdict, status and confidence, with the
call path as evidence. The benchmark asserts separately, ahead of everything
else, that nothing expecting `affected` is ever cleared.

### Done: symbols from fix commits

`core.patchdiff` turns an advisory's fix commit into the set of symbols the fix
changed, which is where vulnerable symbols come from for the 88.7 % of Python
advisories that carry a recoverable commit.

- `references`: picks the best fix reference from an advisory and tiers it, so a
  reference resolving to an exact commit is distinguished from one naming only a
  release.
- `fetch`: a bare `git fetch --depth=2` of one commit, then `git diff` and
  `git show`. Nothing is checked out and no hook, prompt or inherited
  configuration can run.
- `unidiff`, `layout`, `extract`: parse the diff, work out which import names
  the package actually provides, and map each changed line to the definition
  containing it.

One finding from real data changed the design. CVE-2024-45399 affects `indico`,
but its fix commit lives in the `flask-multipass` repository. Symbols extracted
from a path that anchors on no import name the affected package provides belong
to a different package, and using them would drive a verdict about the wrong
code. Those paths now yield nothing and are reported as unmapped.

### Done: dependency graphs, caching, and the whole command

- `core.reach.dependencies`: reads a project's installed distributions from
  their `METADATA`, `top_level.txt` and `RECORD` as text, and builds a graph for
  each one whose installed version matches the inventory. A version mismatch is
  refused rather than graphed, because a graph of the wrong version describes
  code the project does not ship.
- `core.reach.cache`: msgpack serialisation and a sharded on-disk cache keyed by
  package, version and builder version. Written through a temporary file, so an
  interrupted scan never leaves a half-graph behind. A corrupt entry is deleted
  and treated as a miss, because a wrong graph produces a wrong verdict.
- `core.scan` runs the reachability stage, and `vexpath scan` exposes it with
  `--entry-point`, `--environment`, `--no-cache` and `--no-reach`.

Verified through the real command against a synthetic environment: the
unused-transitive fixture reports `2 findings | 0 reachable | 2 not affected`,
and the direct-call fixture reports the path
`app.main.fetch -> requests.get -> requests.api.get ->
requests.sessions.Session.request -> requests.sessions.Session.send`, five
resolved calls into the dependency's internals.

### Done: explaining a single verdict

`vexpath reach --advisory CVE-…` answers the question that follows a scan, and
the one people actually argue about: why did that finding come out the way it
did. It prints the symbols searched for with their provenance and confidence,
which of them exist in the installed version, which entry points reach them
with the call path for each, and the graph the answer rests on.

`core.triage` and `core.scan` build the same graph through the same
`prepare_reachability`, so the two commands cannot disagree. A test asserts it
directly rather than trusting the arrangement.

Operator-supplied symbols are accepted with `--symbol`, which matters for the
11.3 % of Python advisories with no recoverable fix commit. They are recorded
with a `manual` provenance and low confidence, because nothing checked that the
fix touched them.

Writing this command found two wrong statements in the reachable explanation: a
path of five symbols was described as five calls rather than four, and a symbol
that is itself an entry point was described as being called from itself.

### Done: the extraction job, and what the real corpus taught it

`vexpath-worker extract-symbols` walks the advisories awaiting symbols,
fetches each fix commit, and stores what the diff changed. It is a
network-bound crawl over tens of thousands of repositories, so it is built to
be stopped rather than to finish: each advisory's outcome is committed as it is
decided, advisories are grouped by repository so several sharing one reuse a
single bare repository, and attempts are counted and capped at three. A fix
commit in a deleted repository fails identically forever, and without the cap
it would be retried on every run while advisories never tried once waited
behind it.

Running it against 19,548 real PyPI advisories found five things that no
fixture would have.

- **An advisory can carry two `affected` entries for the same package**, one
  enumerating versions and one giving a range. CVE-2014-3555 does this for
  `neutron`. Matching evaluates the first entry that names a package and never
  looks at the rest, so versions covered only by the second produced no finding
  at all, silently. Now an invariant on the `Advisory` model, so a snapshot
  from an older build is corrected on the way in.
- **12,003 of the 19,552 records are malicious-package records**, and they are
  the most recently modified, so they sorted to the front of the queue. Every
  batch would have been spent discovering that a record with no fix has no fix.
  They never enter the queue now.
- **A snapshot's content hash covers the normalised records**, so improving
  normalisation changes the hash of a corpus whose bytes never moved. Reported
  as corruption, which is what happened, that sends a reader hunting for damage
  that is not there. Snapshots record the build that normalised them.
- **The commit cache was only a scratch directory.** Advisories were grouped by
  repository for reuse that did not exist, since each fetch got a throwaway
  bare repository. One repository per upstream is now kept and reused, and a
  reused repository left unusable by an interrupted fetch is discarded rather
  than failing every later advisory that shares it.
- **The symbol-coverage floor warned on every sync.** Coverage is 0 % for a
  freshly downloaded corpus because symbols come from extraction, which is a
  separate job, and the warning said the product's central claim was in
  question. It now says what to run, ignores ecosystems the run did not ask
  for, and ignores denominators too small to mean anything.

A sixth thing came out of the first successful run. Two advisories timed out
at five minutes fetching `cryptography` and `feast`, because a depth-2 fetch
still transfers every blob in both trees even though only the handful of files
the diff names are ever read. Fetching with `--filter=blob:none` and letting
`git show` pull the contents it needs brought those two from two timeouts to
twenty seconds for the pair, with fifteen symbols extracted. Servers without
partial clone refuse the filter rather than ignoring it, so the plain fetch
follows.

Nothing fetched is ever executed: a bare repository, no checkout, hooks and
inherited configuration disabled, and the diff read as text.

Two advisories in five carried only a release tag rather than a commit.
`GitCommitSource.resolve_tag` turns a tag into a commit in one `ls-remote`
call and is tested, but it is deliberately not wired into extraction yet. A
release tag's commit is the release, so diffing it against its parent would
describe whatever that one commit changed rather than the fix, and symbols for
the wrong code are exactly what drives a wrong verdict. Doing it correctly
means diffing the previous release tag against the fixed one, which is the
`tag_diff` symbol source the design reserves for it, at low confidence.
That is the next piece of extraction work.

### Done: getting the symbols to the tool that needs them

A downloaded corpus carries no vulnerable symbols, because OSV does not publish
them. Extraction fills them in but writes to the database, and the command-line
tool reads a snapshot directory. Without a step between the two, the symbols
that make reachability work never reach the thing doing the reaching.

`vexpath-worker export-snapshot` writes the database's corpus back out as a
snapshot, symbols included, in exactly the shape a download produces, content
hash and all. So a deployment runs sync, extract, export, publish, and what it
publishes is a corpus with symbols in it.

### Measured end to end, 2026-11-09

Over 150 real PyPI advisories, taken in queue order:

| Measure | Result |
|---|---|
| Symbols extracted | 1,411 |
| Advisories that yielded symbols | 106 of 150 |
| Symbols per successful advisory | 13.3 |
| Repositories fetched | 56 |
| Needing a tag or pull request resolved | 15 |
| Failed | 0 |

Then the whole path, on a project built for the purpose: pin `nltk==3.9.1`,
install it, write a four-line application that calls `nltk.download`, and scan
it against the exported corpus. The scan reported 43 findings, 41 of them under
investigation because extraction has not yet reached their advisories, and
`vexpath reach` explained CVE-2026-33236 against a call graph of 25,391 edges
built from the installed package.

That last step found a precision bug worth more than the demonstration.

**A class reached only by import is not evidence its methods can run.**
CVE-2026-33236 names nltk's `Downloader` class and its `_download_package`
method. Importing a module executes its class statements, so the class was
reached by three import edges from an application that merely imports nltk, and
the verdict read "reachable_confirmed ... the vulnerable code can run". The
class statement running is not the vulnerable method running. Such a match is
now `reachable_possible`, with the reason printed. A *module* reached by import
is still a confirmation, because when a fix changed module-level code,
importing the module runs exactly that code.

**A class must not expand to methods the advisory did not name.** The same
advisory expanded `Downloader` to all 36 of its members, two of which run
whenever the class is instantiated, so an unrelated method being reachable
counted as reaching the vulnerability. A class now expands only when the
advisory names no method inside it, which is the case where its body is the
only target there is.

Both failures point the same way, and it is the direction this project refuses:
they turn weak evidence into a confident answer. Neither would have surfaced
against a fixture.

### Done: exploitation signals

EPSS probabilities and the CISA Known Exploited Vulnerabilities catalogue,
carried over from M1. They change what to fix first and never what is reported,
which is the asymmetry most of their tests assert.

A sync attaches them to the corpus it writes.
`vexpath-worker enrich-advisories` refreshes them in place over a stored
corpus, because EPSS is recomputed daily and the advisory corpus is not:
re-downloading the OSV exports to pick up new probabilities would be the wrong
trade. Only the four signal columns are written.

Both feeds are keyed by CVE, so lookups go through every identifier an advisory
carries. Most of OSV is GHSA-primary with the CVE as an alias, and matching
only the primary identifier would have lost most of the corpus silently.

A feed being unreachable is reported, never fatal. Failing a sync because a
third party is down would stop a security tool from updating.

Measured against the live feeds on 2026-11-09: 402,199 EPSS scores and 1,772
KEV entries downloaded; of 19,552 stored advisories, 6,714 of the 6,766
carrying a CVE identifier were scored, which is 99.2 %, and 21 are known
exploited.

That number first read 34.3 %, because the denominator was the whole corpus and
12,786 of its records are malicious-package entries with no CVE that no feed
can ever score. The same wrong-divisor mistake as the fix-commit gate in M1,
and it would again have made a working system look broken.

### Done: graphs from the package index

Reachability needs a dependency's own code, and the cheapest source is the
project's installed environment. Two situations have none: a pull-request check
where only the lockfile changed and nothing has been installed, and a benchmark
over many projects where building an environment each costs more than the
measurement. Installing the dependencies would run arbitrary setup code from
every one of them; downloading the wheel and reading it does not.

`--download-missing` fetches a dependency's exact version from the index when
it is absent or at the wrong version, prefers a pure-Python wheel because its
layout is already the import layout, and falls back to an sdist. Reported in
the scan's notes, because a verdict resting on a downloaded archive rests on a
different thing from one resting on the environment the reader is in.

An archive is third-party data that gets unpacked to disk, so most of its tests
are refusals: a member whose path escapes the extraction directory, a symlink
member, an absolute path, a host off the allow-list, a declared size and a
real body above the cap, and a member count that looks like a bomb. Only Python
and metadata files are written at all. Nothing is ever executed, and a test
proves it by unpacking a `setup.py` that would exit the process if it ran.

Verified against the real index: the nltk project from the demonstration above,
scanned with an empty environment and `--download-missing`, reaches the same
verdict with the same evidence as it did with the package installed.

**No clearance broke a soundness precondition.** Every one was checked from

|---|---|---|
| 1,453 symbols across 113 advisories | 113 | 51 of 146 (34.9 %) |

## M3 · VEX, attestation, policy — **in progress**

### Done: OpenVEX generation

`vexpath vex export` writes an OpenVEX 0.2.0 document from a scan's
conclusions. Three modelling decisions shape it.

**A statement is about your product, not about the dependency.** The subject of
"not affected" is the thing you ship, and the vulnerable dependency is a
subcomponent of it. A statement whose product is `pkg:pypi/urllib3@1.26.17`
says urllib3 is not affected by its own advisory, which is false and not the
scanner's to say. This is the part most tools get wrong, and it has its own
test.

**Only one justification is ours to assert.** Reachability establishes that the
vulnerable code is not in the execute path. It does not establish that the
component is absent, that the vulnerable code was removed, that an adversary
cannot reach it, or that a mitigation is in place; those are four different
claims needing four different kinds of evidence. Generating any of them raises
an error rather than publishing a claim nobody tested. The exception is a human
suppression, where a person has asserted the mitigation and stands behind it.

**Every statement carries its evidence.** The specification would accept a bare
justification. A consumer deciding whether to trust someone else's "not
affected" needs the symbols searched for, the number of entry points and how
they were identified, the graph's size and unresolved-call ratio, the
confidence, and the advisory snapshot. An unexplained clearance is one nobody
can check, so all of it goes into the impact statement.

The document is byte-identical for identical results, and its identifier is
derived from its content, so two scans of an unchanged project produce the same
document. That is what lets a VEX document be diffed and what makes its hash
worth attesting.

Verified on the flask benchmark checkout: 38 statements, 28 not affected and 10
under investigation, each clearance naming the symbols it searched for and the
28 entry points it searched from.

Writing it exposed one readability bug. An unreachable explanation inlined
every searched symbol, so a fix touching twenty-five definitions produced a
sentence nobody would read, printed twice in the VEX impact statement. It now
names three and counts the rest; the full list travels in `searched_symbols`,
where it is available without being in the way.

### Done: the policy engine

A scanner that reports is useful; a scanner that gates is what keeps a
vulnerable dependency out of production. `vexpath scan --policy` is that gate,
and `vexpath policy list|explain|test` is how it is written and tried out
before anyone pushes.

CEL rather than a bespoke matcher, because a policy is a thing teams write,
review in a pull request and copy between projects, and a syntax invented for
one tool has to be learned for one tool.

**An expression evaluates to true when the build must fail.** That way round
deliberately: a policy describes what is unacceptable, so a mistake tends
toward a failing build rather than a silently green one. An expression that
returns a non-boolean is a configuration error, not a truthiness test. An empty
policy is refused, because choosing not to gate should be visible, and the
`report-only` preset exists to say so.

**A policy reads only what the scan concluded.** The context is a projection of
the results: no clock, no environment, no filesystem. The same results and the
same policy give the same answer on a laptop and in CI, which is what makes a
local run worth trusting. Every field is present and none is null, so an
expression comparing against a missing value cannot break a build.

**`reach.analysed` is the field that matters most.** Without it a gate cannot
tell "not reachable" from "nobody looked", and treating the second as the first
is how a reachability-aware gate becomes less safe than a naive one.

The five presets, and what each is for:

| Preset | Fails on |
|---|---|
| `strict` | Any critical or high reported as affected, reachability ignored |
| `balanced` (default) | Critical and high whose code was *proven* reachable, plus anything in the CISA catalogue |
| `kev-only` | Only advisories known to be exploited, not cleared |
| `nothing-outstanding` | Anything still needing a human |
| `report-only` | Nothing, said out loud |

`balanced` is the product's thesis as a gate, and it has one deliberate
asymmetry: a KEV advisory whose vulnerable code was proven unreachable still
passes. The catalogue says the vulnerability is exploited somewhere, not that
this project executes the code.

Verified against the flask benchmark checkout: `balanced` passes its 38
findings, because none was proven reachable and none is in the catalogue;
`nothing-outstanding` fails and names each of the ten still open. Exit codes
hold the documented contract: 0 pass, 1 policy failed, 3 for a malformed or
non-boolean policy, with the parse error pointing at the position.

### Done: attestation

A VEX document that says "this does not apply to us" is worth something only
if a consumer can establish who said it. `vexpath attest sign|verify|inspect`
is that, in the shape the ecosystem already reads: an in-toto Statement v1 in a
DSSE envelope, signed keylessly through Sigstore in CI or with a static ed25519
key anywhere.

Three rules, each because the alternative produces a signature that means less
than it appears to.

**A statement must have a subject.** An attestation about nothing in particular
cannot be matched to an artefact, so a verifier cannot tell whether it
describes what they are holding. Building one without a subject raises. With
nothing named, the subject is the document's own digest, which is weaker than
naming a built artefact but is true.

**The signature covers the payload type.** DSSE's pre-authentication encoding
binds both, which is what stops a signed VEX document being presented as a
signed SBOM. The implementation is checked against the specification's own
example rather than against its own output, because an encoding that is almost
right is a vulnerability rather than a bug, and round-tripping with itself
would prove nothing.

**A valid signature is a weaker fact than it sounds.** It may cover a different
artefact, a different kind of claim, or come from a different signer.
`--expect-type`, `--expect-subject`, `--expect-identity` and `--expect-issuer`
close that gap, and the output names which of them were applied. Verifying with
none applied says so out loud, because the common mistake is to read "verified"
as more than it is.

Keyless signing is preferred in CI and static keys are labelled as what they
are: a static-key signature tells a consumer only that whoever holds that key
made the claim. A failure to sign is always reported and never produces an
unsigned envelope, because a pipeline that believes it is signing and is not is
worse off than one that knows it is not.

`attest inspect` describes an envelope without verifying it, and is a separate
command on purpose. A tool that blurs describing and believing teaches people
that a signature's presence is the same as its validity.

Verified on the flask VEX document from the benchmark: signed, verified with
the digest and predicate type required, and then shown to fail on a wrong
predicate type, a wrong subject digest, a payload altered by one character, and
a signature relabelled as another payload type.

## M4 · Hosted platform and public pages — **in progress**

### Done: tenant isolation

One organisation reading another's dependency inventory is the worst thing
this platform could do. An inventory names every library a company depends on
and every version it is behind on, which is a map of where to attack them. So
this was built before any endpoint that could leak it.

Isolation is not a `WHERE` clause. A filter that has to be remembered is one
that will be forgotten, in a new endpoint written in a hurry, and nothing will
fail until a customer notices. Postgres enforces it on every statement,
including the ones nobody has written yet.

Three things make that real, and leaving out any one makes the rest
decorative:

1. **A policy on every tenant table**, comparing `org_id` against a session
   setting. `current_setting` returns NULL when unset and `org_id = NULL` is
   NULL rather than true, so a request that forgot to establish a context sees
   nothing. Failing closed is the only acceptable direction.
2. **`FORCE ROW LEVEL SECURITY`**, because a table's owner is exempt from its
   own policies by default and the owner runs the migrations.
3. **A non-privileged role.** A superuser bypasses row-level security
   entirely, and the local development user is one. The application connects
   with the owner's credentials and immediately switches to `vexpath_app`,
   which is `NOLOGIN` and `NOBYPASSRLS`, so there is no second password to
   provision or leak and nothing can connect as it directly.

The context is written through `set_config` with a bound parameter, in one
helper, because `SET` takes no parameters and building that statement by
concatenation would turn a tenant identifier from an HTTP request into an
injection point.

**The public read path is a separate setting, not a relaxation of the first.**
A tenant context answers "what may this organisation see"; a public context
answers "what has been published". Entering either clears the other, so a page
serving a public report cannot serve it with a tenant's context attached.
Public policies exist on nine tables and on none of the others: users, API
keys, policies and suppressions have no public policy at all. A suppression in
particular says "we know about this and chose not to fix it", which is an
invitation.

Each public policy is an `EXISTS` up the chain to `projects` rather than a flag
on the row. A flag would have to be kept in step on every write, and the one
time it was not, a private project's findings would become world-readable.

**The acceptance criterion, met:** 82 automated negative tests. For every one
of the seventeen tenant tables, one organisation asks for another's rows
directly by identifier, asks with no context at all, and tries to write a row
carrying the other's identifier. A structural test asserts every table the
metadata calls a tenant table has row-level security enabled, forced, and a
policy, so a table added without protection fails the suite rather than
quietly leaking. The audit log additionally has no `UPDATE` or `DELETE`
privilege, because an actor who can rewrite their own audit trail has none, and
the application cannot write to the advisory corpus at all, because an endpoint
that could change an advisory could change a verdict.

### Done: API keys, projects and scan upload

The three pieces a CI job needs to get its conclusions onto the platform.

**Authentication and scoping are one dependency, not two.** An endpoint
obtains a database connection only through a dependency that authenticates and
then puts the organisation into the session, so there is no arrangement of
dependencies that yields a request which is authenticated and unscoped. That
combination is the shape of a data leak, so it is made unreachable rather than
discouraged.

**A key is a bearer credential, so the handling follows from that.** Only the
SHA-256 is stored and the secret is shown once, which means a database
disclosure hands over no working credentials. A plain hash deliberately, not
bcrypt: the secret is 256 bits from the system random source, so guessing is
not the threat and a slow hash would only add latency to every request. The
prefix is stored in the clear so a dashboard can tell two keys apart, and is a
fixed recognisable string so secret scanners match it.

**Every authentication failure says the same thing.** A caller learns the key
does not work, never whether it was unknown, revoked or malformed, because
each of those narrows a search. The comparison is constant-time and runs even
when no key was found, against a fixed value, so timing does not reveal which
identifiers exist.

**The organisation comes from the credential, never from the request body.** A
caller who could name it could create a project inside someone else's
organisation, and the policy would then happily let them read it back. A
project is private until someone says otherwise, because a default of public
would publish a dependency inventory by omission.

**A project that is not yours is 404, not 403.** Saying it exists but is not
yours turns the endpoint into a way of asking whether a competitor uses this
platform and what they call their services.

**An upload is validated through the same model the analysis produced**, so a
malformed or hand-edited document is refused at the boundary rather than
becoming rows nothing can interpret, and a document asserting a clearance the
analysis never established is refused by the model's own invariant. The whole
ingest is one transaction: a half-stored scan would show findings whose
evidence is missing, which reads as "nothing to see here" rather than as a
broken upload.

Fifty tests, against real HTTP and a real database. Most of them try to cross
the boundary: every endpoint is asked to show one organisation the other's
projects, scans and findings.

Two real problems came out of writing it. Windows defaults to an event loop
psycopg's asynchronous mode cannot use, which is now set once in the platform
package for the process entry point and the tests alike rather than
rediscovered by whoever runs the API on Windows next. And the 422 handler used
a status constant Starlette has deprecated, which under this project's
warnings-as-errors policy turned a correct refusal into a 500: the policy
caught a bug that would otherwise have shipped as an intermittent server error
on malformed input.

### Done: findings, the public report page and the badge

**The findings endpoint carries its evidence inline.** A client that has to
make a second request for the call path will render a list without it, and a
list of verdicts with no evidence is indistinguishable from any other
scanner's output. One query joins the component and the reachability result,
because two hundred findings each fetching their own evidence is two hundred
round trips.

Cleared findings are returned rather than hidden. The point of the analysis is
a short list and the ordering puts what needs attention first, but a clearance
a consumer cannot see is one they cannot check, and "we removed 28 of your 38
findings" is exactly the claim that needs checking.

**The public report page is complete in its first response.** No script, no
fetch, no deferred list, asserted by inspecting the markup rather than by
trusting the template. A report whose content arrives later cannot be read by
a crawler, a feed reader, a text browser, or anyone whose second request did
not make it, and the entire reason to publish a report is that other people
can read it.

The page states how much to trust it: whether the advisory corpus was pinned,
and that an uploaded result is self-reported until something verifies it. A
report that implied otherwise would be the most consequential thing on it to
get wrong.

**The badge is pessimistic wherever the answer is not known.** It is the most
widely copied artefact a project publishes, seen by everyone who looks at the
repository, so one that said "clear" on the strength of an unreproducible scan
would mislead at the greatest possible scale. A scan with nothing reachable
but no pinned corpus reads "none reachable (unverified)" in the cautious
colour. The SVG is generated here rather than by redirecting to a badge
service, because a redirect would tell that service every repository that
embeds one and which of them are looking at a vulnerable dependency, and it
references nothing external for the same reason.

**The package page is built entirely from the global corpus**, so it needs no
organisation in scope and is useful to somebody who has never uploaded
anything: it answers "which functions did this advisory's fix change", which
is the part nobody else publishes.

Verified end to end on the real flask scan: 38 findings uploaded through the
API, the report page rendering 30 KB of complete HTML with 28 clearances and
their searched symbols, and the badge reading "10 unknown" rather than
claiming a clean bill of health.

Twenty-three tests cover it, including that a private project has no report
page and no badge, that unpublishing withdraws both, and that a project which
does not exist answers identically to one that is not published so nobody can
enumerate private names.

### Done: the command-line loop

The platform accepted scan uploads and nothing in the command-line tool could
send one. That is not a missing feature, it is two halves that do not meet, and
until they do each one is demonstrable and the product is not.

**A key is read from `$VEXPATH_API_KEY` before the stored file.** CI supplies
it from a secret, and a stale credential file on a shared build machine must
not shadow it. Every command says which source won, because "which key am I
using" is the question behind most authentication confusion and the answer is
almost always that one place quietly overrode another. `logout` says plainly
when an exported key means you are still signed in.

The secret is never printed — not in a confirmation, not in an error, not in a
`repr`, which matters because tracebacks are produced exactly when attention is
elsewhere. The file is written through a temporary file whose permissions are
restricted before any content reaches it, and its path appears in the output of
every command that touches it: a credential nobody can find is one nobody
rotates. `login` verifies the key against `/v1/me` before storing it, so a typo
fails now rather than as an unexplained rejection three commands later.

`scan --upload` resolves the credential **before** the analysis starts, so the
two mistakes that would otherwise throw away a four-minute scan are reported in
a second. It uploads before the policy decides the exit code, because the scan
the platform most needs is the one that just failed a gate. A refused upload
still says the scan itself completed: the exit code cannot say it, and a CI log
read in a hurry would otherwise be understood as the analysis having failed.

`vexpath upload` exists for the pipeline that scans in one job and uploads in
another, and validates the document through the same model the server uses, so
a truncated artefact is described in terms of the file rather than as a 422
naming a field nobody chose.

### Done: signing in, sessions and the first screens

**The JSON API takes a bearer key, the HTML pages take a cookie, and no
endpoint accepts both.** That separation is the security of the whole UI. A
browser sends its cookie automatically on any request to this origin, including
one another site caused, which is what cross-site request forgery is; an
endpoint that accepted either credential would hand that problem to every
caller. `/v1` refuses cookies, the HTML routes refuse keys, and both directions
are asserted.

**The OAuth state parameter is verified before the authorisation code is
exchanged.** Without the parameter, an attacker completes a flow with their own
code in a victim's browser and the victim ends up signed into the attacker's
account, uploading their dependency inventory to it. Without that *ordering*,
the code has already been spent by the time the forgery is noticed. The state is
signed and time-limited rather than stored, so it needs no table and no cleanup,
and it carries the page the user was trying to reach so signing in resumes what
they were doing. It cannot carry them off-site: anything that is not a
single-slash-rooted local path is discarded, because "you were signed out, sign
in again" phishing works precisely by making the link point at the real site.

**The account is keyed on GitHub's numeric subject, never the login.** A login
can be renamed and the old name claimed by somebody else, so keying on it would
eventually sign one person into another person's account — the worst thing an
identity layer can do. There is no password column to forget to hash.

**Every form carries a CSRF token**, derived as an HMAC of the session
identifier rather than stored, so nothing can fall out of step and no token can
outlive its session. `SameSite=Lax` already blocks the cross-site POST; this is
the second lock on the same door. Domain separation keeps a CSRF token from
being a valid state parameter, which it otherwise would be.

**A new key's secret is shown on the page that created it and never again**,
and the page is the response to the POST rather than a redirect: a redirect
would carry the secret in a URL, into browser history, into any proxy log on
the way, and into the next request's `Referer` header. Only the SHA-256 is
stored, so the claim that it cannot be shown again is literal rather than
a policy.

The identity provider is an interface with a real implementation and a
stand-in, so every branch of the flow is tested without a network: a cancelled
authorisation, a forged state, a provider that errors, a GitHub account with no
verified address. Those are the branches that otherwise answer 500 the first
time a real person meets them.

Nothing in these pages is JavaScript. Not "works without it as a fallback" —
there is none to fall back from. Every action is a form POST to its own URL
answering with a redirect, which still works in a text browser, with a screen
reader, and under a content-security policy that forbids script.

**The loop closes**, and there is one test that says so: sign in, create a
project, issue a key on the keys page, and upload a scan with that key through
`/v1/scans`. Each half was already covered; what silently fails is the join,
when two halves are built a week apart.

Sixty-two tests cover it — 41 through real HTTP and a real database, 21 on the
token primitives — plus two more negative row-level security tests, because
`sessions` is a tenant table and one organisation reading another's session
rows would be account takeover rather than a leak.

### Done: the evidence pages

The screen the product exists for. Every scanner can list advisory
identifiers; what nobody shows is *why* a finding was kept or dropped, and
that is the only part a person can check.

So these pages follow one rule: **a verdict is never shown without the
evidence for it.** A reachable finding shows the path hop by hop, with the
file and line of each call. A cleared finding shows the symbols that were
searched for and the entry points the search began from, because "not
reachable" means nothing unless you know what was looked for and from where.
Each page publishes the quality of the graph the answer rests on -- the
unresolved-call ratio above all -- so a verdict can be judged rather than
trusted.

**Three situations are never collapsed into each other:** a proven path, a
path that depends on a call resolved conservatively, and no analysis at all. A
single dynamic hop is marked on the path itself, because it is the difference
between a proven path and a guess. A finding with no reachability row says
"Nobody looked" in those words, and says that this is not the same as "not
reachable" -- the two produce the same short list of things to fix, and
conflating them is how a scanner quietly hides a real vulnerability.

Cleared findings are listed rather than hidden. "28 of your 38 findings cannot
run" is exactly the claim a reader should want to check, and a clearance
nobody can inspect is one nobody should believe.

The call path is an ordered list rendered server-side. A viewer drawn by
script would be invisible to a crawler, to a text browser, and to anybody
reading a saved copy, and the whole value of evidence is that it travels.

Twenty tests, including that a stored path containing junk renders the hops it
can and drops the rest: the row came from an uploaded document, and the page a
developer opens when something is already wrong must not be the one that
answers 500.

### Done: suppressions

Deciding not to fix something is a legitimate and common decision, and a tool
that offers no way to record it gets one anyway — as a `grep -v` in a CI
script, as a threshold nobody revisits, or as a team that stops reading the
output. So this exists, shaped around the two ways it goes wrong.

**A suppression with no expiry outlives the reason for it.** The column is not
nullable, the duration is capped at 730 days, and the page says "expires in 11
days" rather than a date, because one is a prompt and the other is just a
date. Somebody has to look again, which is the only property separating a
suppression from a deletion.

**A suppression with no reason cannot be reviewed**, and an unreviewable
suppression is how a vulnerability stays hidden after the person who hid it
has left. Blank text is refused by the API and by the form, and the refusal
says why rather than naming a field.

Scope is the component by default. A project-wide suppression also covers
packages added next month, which is a bigger decision than the button it would
otherwise share, so it is a separate checkbox. Matching is exact on the purl:
a prefix match would let a suppression written for one package quietly cover a
differently-named package added later. The most specific one wins, so revoking
a broad suppression does not silently unsuppress something that had its own
entry.

**And a suppression never changes the facts.** Not the verdict, not the
severity, and not what the public report or badge says about reachable code —
there is a test that suppresses a reachable finding and asserts the badge
still reads "1 reachable". A badge saying otherwise would be the most
misleading artefact this system could produce. It also cannot change a CLI
exit code, because the CLI evaluates its policy locally with no knowledge of
the platform; that is stated in the documentation rather than left for
somebody to discover.

Every create and revoke is written to the audit log with the reason as it was
given. "Who decided not to fix this, and what did they say at the time" cannot
be answered by a row that only holds the current state.

Twenty-nine tests: eleven on the rules with no database, eighteen through real
HTTP, including that the page refuses to echo a sentence from its own query
string — autoescaping stops markup, not a phishing message.

### Done: rate limiting

Stated plainly, because a limiter sold as protection it does not provide is
worse than none: this does **not** defend an API key against guessing. A key
is 256 bits from the system random source; there is no rate at which guessing
becomes feasible, and implying otherwise would invite somebody to shorten the
key. What it defends against is a misconfigured CI job retrying in a tight
loop, a scraper walking the public pages, and the cost of either.

**The counter table is bounded.** An unbounded map keyed by a value the caller
chooses is a denial of service with extra steps, and it is the usual way a
hand-written limiter becomes the vulnerability it was added to prevent. The
map is capped and evicts the oldest entry, so the failure mode is "that client
stops being limited" rather than "the process dies" — and eviction is by age,
so a client still sending is the one that stays tracked.

**`X-Forwarded-For` is not believed by default.** It is a request header like
any other. Trusting it without a proxy in front lets a caller evade their own
limit by varying it and, worse, exhaust somebody else's allowance by claiming
their address. A deployment behind a known proxy turns it on, and then only
the last hop is used — the one the proxy wrote.

The identity is the credential before the address, so one organisation's
runaway job cannot consume another's allowance merely by sharing an office
network or a CI runner. An API key is identified by sixteen hex characters of
its hash and never by the key: a limiter whose state a heap profile would show
must not be a place credentials are kept.

A refused request still counts, so a client that keeps sending stays refused
rather than discovering that rejections are free. `Retry-After` is the real
number of seconds to the window turnover, never zero. Health checks are
exempt, because a liveness probe answered with 429 takes the instance out of
service and turns a rate limiter into an outage.

The state is per process, which is a real limitation written down rather than
hidden: two instances each allow the configured rate. The alternative, a
shared counter in Postgres, costs a write on every request, and that trade is
worth revisiting when there is a second instance.

Twenty-two tests.

### Done: the OpenAPI document, committed

`apps/api/openapi.json`, regenerated with `make openapi`. Committed rather
than only served, because a committed document turns an accidental breaking
change into a diff somebody has to look at: a renamed field, a narrowed type
or a dropped endpoint shows up in review, where it is cheap, rather than in a
client's CI, where it is not. A test asserts the file equals what the
application would serve, so it cannot drift, and the failure message says to
run the exporter and read the diff.

Serialised with sorted keys and a trailing newline, so a real change produces
a diff of the change and not of a reordering. Only `/v1` is described: a
schema listing pages nobody calls programmatically makes the part people do
call harder to read. One test walks every response model for a field named
like a credential, because the one response in a key's life that carries its
secret comes from a page that is not in this schema — if such a field ever
appears here, something is being returned that should not be.

### Done: webhooks

The one feature where a user hands the platform an address and it connects to
it, which makes it server-side request forgery by design. The whole of the
design is therefore refusals, and each one closes a specific bypass rather
than being a preference.

`169.254.169.254` has its own test. It is link-local rather than private, so a
check that asked only `is_private` would allow the cloud metadata endpoint
that hands out the instance's credentials — the single most valuable address
on the internal network and the one a naive allowlist misses. Loopback written
as `::ffff:127.0.0.1` has its own test for the same reason.

**Every address a hostname resolves to is checked, not the first.** A name
resolving to one public and one loopback address would otherwise pass and then
connect to whichever the socket picked. **And it is resolved again on every
delivery**, because a name that resolved publicly an hour ago can resolve to
`127.0.0.1` now; validating once at registration is the DNS rebinding bypass.
A narrow window remains between that check and the HTTP client's own
resolution, and it is written down in the module rather than left for somebody
to assume it is not there.

Redirects are refused, not followed: a redirect is a second URL that nothing
validated, which is how all of the above would be bypassed. It is recorded as
*refused* rather than *failed*, because "we would not connect there" and "they
did not answer" need different fixes and a log calling both failures sends
somebody to check their server when the problem is their address.

**The signature covers a timestamp and then the body**, separated so the two
can never run together — without a separator, timestamp 1 with body `23` and
timestamp 12 with body `3` would share a signature. The timestamp travels as a
header too, which is what lets a receiver refuse a replay; signing the body
alone would make any captured delivery valid forever.

**The secret is encrypted at rest rather than hashed**, because an HMAC needs
it back. That is the one place in this system where a credential is
recoverable, so the threat model is stated: it defends a leaked backup, a
snapshot in the wrong bucket, an open replica, SQL injection — cases where an
attacker holds rows and not the process. It makes no claim against an attacker
who has the process, because that attacker has the key. Rotating
`VEXPATH_SECRET_KEY` therefore makes stored secrets unreadable, and the
delivery says "re-issue this secret" rather than looking like the receiver's
fault.

Three attempts, then stop: beyond a restart and a blip the receiver is down,
and a sender that keeps trying is a load generator aimed at somebody already
struggling. Twenty consecutive failures disables the webhook rather than
deleting it, so somebody can see why it stopped. Deliveries go out after the
response to the upload that caused them, because a CI job must not fail
because a chat integration is down.

The resolver and the HTTP transport are injectable, and nothing in the
application passes either — so there is no flag that could weaken this in a
deployment, and a test can still answer with one public and one loopback
address, which is the bypass that matters and the one real DNS will never hand
you on demand.

127 tests: 85 on the URL rules, the signature and the secret box with no
database, 42 through real HTTP, plus two more negative row-level security
tests for the new tenant tables.

### Done: the webhooks screen and the scan diff

**The webhooks screen exists so the refusals reach a person.** A URL field
that answers "not allowed" sends somebody to a support channel; one that says
which rule and why is the difference between a security control and an
obstacle. The rules are on the form before they are broken — https, a public
address, port 443, no redirects — and a refused URL comes back with the whole
explanation and the value still in the field. The signing secret appears on
the response to the POST and never again, with the HMAC construction and the
constant-time warning printed beside it, because that is the moment somebody
is writing the receiver.

The delivery history is on the same page rather than behind a link. "I
registered it and nothing arrived" is the only question anybody asks about a
webhook, and the answer is always in the last few attempts: refused for an
address, failed with a 500, or delivered and the receiver dropped it. A
disabled webhook says it was switched off after repeated failures, and
re-enabling clears the count — without that, the next delivery's first retry
would switch it off again.

**The diff answers the question somebody actually has after a build**, which
is not "what is wrong with this project" but "what did my change do". Four
sections in reading order: appeared, changed verdict, gone, and a count of
what stayed the same.

"Changed verdict" is its own section rather than folded into "unchanged",
because a finding that moved from not-reachable to reachable is the single
most important line the page can carry and a diff of identities alone would
not show it at all. Identity is the advisory *and* the component purl,
version included, so an upgrade from 1.0 to 1.1 reads as the old finding gone
and a new one arrived — the truthful answer, since the same advisory against a
different version is a different fact and collapsing them would hide an
upgrade that fixed nothing.

Computed on view rather than stored at ingest: a stored diff is correct only
against whichever scan happened to precede it at the time, and recomputing
means the page is right even for a scan uploaded out of order, which happens
whenever two branches build at once.

Twenty-one tests.

### Done: request correlation and error reporting

**One access line per request**, after it finishes, with the request id,
method, route template, status and duration. One line rather than two: a start
line plus an end line doubles the volume to make hung requests visible, and a
hung request is already visible as a missing line beside a complaining client.
What a start line would have added, the request id gives for free — every line
emitted *during* the request carries it, because it is bound into a context
variable rather than threaded through call signatures.

**The route template, never the literal path.** A slug or an advisory
identifier in a URL is tenant data, and the threat model keeps tenant data out
of the logs. It is also the only form that answers "how slow is the finding
page" without a regular expression. Unmatched paths are logged as
`<unmatched>`, which is worth telling apart: a flood of them is somebody
scanning.

**A presented request id is honoured only behind a trusted proxy, and
sanitised either way.** The id goes into every line for the request, so a
newline in it forges a second line into the stream somebody reads during an
incident — there is a test that tries exactly that. An attacker who can choose
the id can also make their requests share one with somebody else's, which is
why it needs the same opt-in as `X-Forwarded-For`. The id is returned in a
response header, because a user quoting it in a bug report is the difference
between a five-minute search and an afternoon of guessing.

**Error reporting is off unless a DSN is configured**, which is the right
default for a tool people run against their own code. When it is on, three
things that would default the other way are off, and each one would ship
something the threat model forbids: request bodies (a scan upload's body *is*
a dependency inventory), cookies and headers (a live session, a live key), and
stack-frame locals (a frame inside the scanner holds the source it was
parsing). A scrubbing hook is the last line rather than the only one — it
drops the request section wholesale and redacts credential-shaped keys at
every depth, because the three settings above can be re-enabled by somebody
who does not know why they were off. A DSN configured without the library
installed says so rather than pretending: a deployment that believes it has
error reporting and does not is worse off than one that knows it has none.

Twenty-three tests, including that a cyclic or absurdly nested event does not
turn error reporting into a hang.

### Done: the policy editor

A gate's mistakes are invisible in both directions: too loose and nobody
notices, too tight and the build everybody needs is red. So the editor's main
feature is not the text box, it is the **dry run against the project's last
real scan** — "would have failed, blaming these three findings" is the only
thing that tells you which kind of gate you have written.

**It says what it is not.** The gate runs in CI, locally, with no knowledge of
this platform, because a build must not depend on a dashboard being reachable.
So the page composes and tests the expression and shows the command to put it
in. Inventing a server-side gate that silently disagreed with the one in CI
would be worse than having none, and that is stated on the screen rather than
left to be discovered.

**An expression that will not compile is never stored.** A gate nobody can
evaluate must not be recorded as a gate, because the next person to read the
configuration would believe it was one. **And one that cannot be evaluated
against real findings is reported as an error, not as a pass** — the same rule
as the command line's exit 3: a gate that failed to run must never look like a
gate that was satisfied.

A preset is stored as its *expression*, never its name: a preset whose meaning
changed in a later release would otherwise silently change what a project
gates on. Saving adds a row rather than editing one and writes the expression
to the audit log, because "who loosened the gate, and when" needs an answer
months later — `false` is a valid policy and the loosest one there is.

**The variables are the same ones CI sees.** The platform keeps findings as
rows rather than the uploaded document, so it rebuilds the context from those
rows; a field present in one builder and absent from the other would change
what an expression means between the two places it runs, and an expression
that errors is a build failing for the wrong reason. The core now publishes
its field vocabulary and a test asserts the two agree, field for field,
including the nested `reach` object. Nothing is ever null in either, because a
policy comparing against null errors at evaluation time.

Twenty-four tests, three of them about that parity rather than about the page.

### Done: the browser acceptance suite

Seventeen tests that drive a real server with a real Chromium. Everything
else in the repository asserts what a handler *returns*; these assert what a
browser can *do* with it, which is a different claim — a page can return
perfect HTML and still be unusable because a form posts to the wrong place.

**The JavaScript-disabled context is the one that earns its keep.** Signing
in, creating a project, issuing a key, publishing, registering a webhook,
saving a policy and signing out are each exercised in a context created with
`java_script_enabled=False`. Not as a fallback — there is nothing to fall back
from — and one added HTMX attribute without a form around it would pass every
other test in the repository while breaking the interface for a text browser,
a screen reader and anybody with a script blocker. A further test walks seven
pages asserting no `<script`, `onclick` or `onsubmit` anywhere.

The public report is fetched **without a browser at all** and asserted to
contain the findings, and with a browser the request log is asserted to hold
exactly one document request: a report whose content arrives in a second
request cannot be read by a crawler, and publishing it is pointless if it
cannot be read.

**It found a real bug that no unit test could.** Since 0.36 uvicorn builds its
event loop from its own factory and ignores the installed policy; on Windows
that factory hardcodes the proactor loop, which psycopg's asynchronous mode
cannot use. So `uvicorn vexpath_api.main:app` — the documented command, the
Makefile target and the Dockerfile's `CMD` — could not reach the database at
all on Windows: `/readyz` reported the database down while the process looked
healthy, and every page that touches it failed. The fix is a loop factory of
our own passed as `--loop`, now used by the Makefile, the Dockerfile, the
compose file and the test server alike, with the reason written where somebody
will find it.

Two of the test's own bugs are worth recording, because both looked like the
product being broken: Playwright's `text=` selector matches *substrings*, so
"Publish" also matched a project named `published` and "Save" matched the
sentence "Saving stores the expression". Every control is now addressed by
role and exact name, and the project in the publishing test is still called
`published` on purpose.

The suite **skips** rather than fails when the browser is absent, naming what
to install. A suite that could not run without a 150 MB download is a suite
most people never run. `make e2e` installs it and runs them.
